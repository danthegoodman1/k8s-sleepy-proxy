# Failure fixture: retained PV binding

The frozen-image failure is explained by actual Kubernetes binding. The test's PV had capacity `1Mi`, while its explicitly prebound PVC requested `2Mi`. Both became `Bound`; the PVC reported capacity `1Mi` and Kubernetes emitted `ExternalExpanding`. The application then became ready and correctly returned HTTP 200. Initial `Pending` was a transient state, not proof that binding could not complete.

## Retained diagnosis

The first failure is retained in [the 03:17 gate log](20260908T031723Z-failures.log) and [metadata](20260908T031723Z-failures.json). Root reproduced it against the same frozen images in `sleepypods-e2e-binding-diagnose`: [03:22 diagnostic log](20260908T032222Z-binding-diagnostic.log), with the driver failing after 39.96 seconds because the one request received HTTP 200 and `sleepypods-stateless-app`.

Read-only capture used the task kubeconfig and exact diagnostic namespace, plus the task-owned `failure-unbound-pv`. No Secret objects or rendered credential values were queried. [Capture time](captured-at.txt), [PV](pv.json), [PVC](pvc.json), [events](events.json), [focused events](unbound-events.json), [sanitized Pod status](pod-summary.json), [control-plane log](control-plane.log), and [frontline log](frontline.log) retain the observations. The initial Pod jsonpath command failed; the subsequent sanitized status capture succeeded. [Database metadata](db-state.txt) shows instance `Running`, generation 2; materialization `Ready`, instance/projection generation 2, backend generation 1, with no recorded failure. The PV/PVC bound at 03:24:02; the workload Pod was created/scheduled at 03:24:04. Ordinary idle cleanup later removed the PV before any experiment mutation.

The server was Kubernetes v1.34.0 ([version](version.json)). Its [persistent-volume controller](https://github.com/kubernetes/kubernetes/blob/v1.34.0/pkg/controller/volume/persistentvolume/pv_controller.go#L404-L445) checks capacity for a requested PV without a claim reference. A matching prebinding instead finishes binding. [Claim matching](https://github.com/kubernetes/kubernetes/blob/v1.34.0/staging/src/k8s.io/component-helpers/storage/volume/pv_helpers.go#L138-L151) requires the UID to match when the PV specifies one. This explains the observed binding and supports a deterministic UID-mismatch fault. The production reconciler still waits for raw PVC `Bound` before applying the Service/workload; this packet changes no production behavior or render policy.

## Test-only correction

[The patch](fixture.patch), relative to the captured [pre-change fixture](fixture-before.rs), changes only `crates/control-plane/tests/kind_e2e_failures.rs`:

- Keep the exact recorded PV/PVC names, same namespace, `volumeName`, Retain policy, and stable projection ownership assertions. Use equal `1Mi` capacities.
- Reserve that task-owned PV for explicit previous-claim UID `00000000-0000-4000-8000-000000000001`. The current PVC must have a different, nonempty UID. This is a controlled stale reservation; no foreign PVC is created.
- Require both current-PVC `Pending` and Kubernetes `FailedBinding` for that exact current UID, naming the expected PV and reporting another claim reservation. A transient Pending snapshot alone no longer passes.
- Preserve the single bounded HTTP request, HTTP 503 without application body, eventual Failed state, no ready backend/workload, and safe inventory cleanup checks. Preserve the separate duplicate-volume pre-acceptance rejection proof.
- Run the same raw inventory through the real renderer and projection plan. The local regression checks the retained reservation and rejects missing/current claim reference UID and an equal live/prior UID.

[Local renderer/projection test](local-test.log): 1 passed, 1 deployed test filtered out. [Scoped clippy](clippy.log) and [format check](fmt.log) passed, as did shell syntax and `git diff --check`. The fixture source has explicit skeptical source/local approval; the successful deployed evidence below was submitted for final review.
