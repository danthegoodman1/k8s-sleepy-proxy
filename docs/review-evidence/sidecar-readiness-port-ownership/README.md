# Sidecar readiness fixture port ownership

The final workspace checkpoint failed one negative startup assertion because it connected to an address the fixture no longer owned. `unused_addr()` bound localhost port 0, returned its address, and dropped the listener. The failing test supplies an indefinitely pending initial control-plane connection and immediately cancels; `run_with_connection` cannot reach either production bind before that dependency completes. Its successful return therefore does not establish ownership of the unrelated endpoint subsequently probed. The original successful connection's peer identity was not captured; no specific competing socket or process is attributed here.

The full [original workspace output](original-workspace.log) and [check record](original-checks.json) are retained. A deterministic scratch [controlled-reuse patch](port-reuse-red.patch) binds a test-owned competing listener to the released proxy address, then executes the same pending-connection cancellation and original assertion. The [red run](controlled-reuse-red.log) reproduces that exact assertion failure in 0.01 seconds. This demonstrates the fixture mechanism without identifying the peer behind the original natural success.

## Correction and evidence

The [three-file patch](fixture.patch) changes `crates/sidecar/src/bin/sidecar/readiness_tests.rs` and the two adjacent library assertion sites explicitly approved by the coordinator: `crates/sidecar/src/readiness/tests.rs` and `crates/frontline/src/listener/tests.rs`. All three modules are behind unchanged `#[cfg(test)]` declarations. There are no production body, API, timing-policy, manifest, dependency, image, or cluster changes. The repository's coarse 148-file digest includes these test modules and changed; that must not be mistaken for a deployed runtime change. [Before/after source hashes and validation](validation-summary.json) identify the exact scope.

- The two never-publish tests retain exclusive, bound-but-not-listening `TcpSocket` guards for proxy, app and health addresses. Cancellation must return `Ok`; the stalled setup must return exactly `tokio::time::error::Elapsed`. An erroneous early bind would fail with `AddrInUse`, so either wrong behavior still fails the test. Guards remain owned through these result assertions. Redundant raw connect probes no longer test a released endpoint or wait for an OS refusal.
- The delayed control-plane test retains proxy and health guards inside the pending connection future until the intended handoff. It asserts that startup is still pending, then preserves the real health 503→200 and single application-request response/count checks. The application starts by calling `listen` on its held socket, with no release/rebind interval. A health connection established before shutdown must close after the owned runtime joins; no new post-close connection is attempted.
- The metrics-failure test retains its exact `AddrInUse`, shared shutdown and bounded joined-return checks. An early proxy/readiness bind failure occurs before shared shutdown is signaled, so it cannot masquerade as the expected metrics sibling failure. The idle-report test retains its bounded joined return and exact client-drop proof. Their redundant fresh connects after releasing listener ownership are removed; these assertions now rely on the already-owned listener futures completing, not an unrelated endpoint lookup.
- One focused reservation regression proves that a competing listener cannot bind the held address and that the same reserved socket can become a listener and exchange an exact marker without releasing its port. Its dial and read are bounded.

An initial scratch revision retained direct refusal probes against nonlistening reservations. [That run](scratch-readiness-tests.log) passed but took 15.61 seconds. When extended to the delayed-start case, the same unbounded probe pattern outlasted initial CP setup and produced a [retained harness failure](scratch-bin-initial-error.log); [source](scratch-before-probe-removal.rs) is retained. The reviewed correction removes redundant OS probes rather than widening setup/test deadlines. It does not identify the kernel's reason for the observed connect delay.
